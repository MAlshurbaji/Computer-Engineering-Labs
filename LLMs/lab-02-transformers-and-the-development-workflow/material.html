Guided task 01

Transformer families and visibility

Transformer families differ in how information can flow between token positions. A typical encoder can use both earlier and later input positions to build representations of a supplied sequence. A causal decoder restricts a position to itself and earlier positions in its own sequence. An encoder-decoder system additionally lets decoder positions consult encoded source positions through cross-attention.

Draw these permitted connections for a five-unit source note and a three-unit output. Rows identify receiving positions and columns identify positions that may supply information. A one indicates permission, not an attention weight or a measured importance score. The decoder's upper triangle is excluded so its prediction cannot directly inspect later target units. Cross-attention can consult the complete already supplied source, which is a different sequence from the partially generated output. These are standard conceptual patterns, not an assertion that every model called an encoder has identical settings. Later labs calculate actual attention weights and implement the decoder-only path used in this course. Here the goal is to distinguish the input/output relationships before following tensor operations.

Try it

  1. Create full source visibility, causal output visibility and source-to-output visibility maps.
  2. Label the receiving and supplying axes explicitly.
  3. Compare permission patterns without interpreting them as learned weights.
Python · run in order
source_length, output_length = 5,3
encoder_visibility = torch.ones((source_length,source_length),dtype=torch.bool)
decoder_visibility = torch.tril(torch.ones((output_length,output_length),dtype=torch.bool))
cross_visibility = torch.ones((output_length,source_length),dtype=torch.bool)
fig, axes = plt.subplots(1,3,figsize=(11,3.5))
for ax,allowed,title in zip(axes,[encoder_visibility,decoder_visibility,cross_visibility],["Encoder source self-view","Decoder causal self-view","Decoder view of source"]):
    ax.imshow(allowed.numpy(),cmap="Blues",vmin=0,vmax=1)
    ax.set_xticks(range(allowed.shape[1]))
    ax.set_yticks(range(allowed.shape[0]))
    ax.set(xlabel="Supplying position",ylabel="Receiving position",title=title)
fig.tight_layout()

Read the result

The cross-attention rectangle and causal self-attention triangle answer different visibility questions. A permitted cell does not specify how much a trained model will use that connection.

Change and compare

  • Count the permitted cells for each of these three maps.
  • Explain why a complete source note can be visible while future output units remain hidden.

Guided task 02

Decoder-only tensor contracts

A decoder-only model accepts token IDs and produces scores over a vocabulary at each processed position. Four dimensions recur throughout this course: batch size B, sequence length T, hidden width D and vocabulary size V. Token IDs have shape B by T. Internal representations usually add a feature axis D, while vocabulary scores use V on the final axis.

Instantiate shape placeholders for the tiny configuration in setup and count their scalar entries. These zero-filled arrays are storage examples, not representations computed by a transformer or meaningful language predictions. The chart shows how expanding a final axis changes the amount of data represented, even while batch and position counts stay fixed. A vocabulary score is not automatically a probability; a later normalization supplies that interpretation. During next-token training, a score vector exists at each input position, while a generation step commonly uses the final valid position's vector. The precise label shift and padding policy matter and will be implemented explicitly later. Learning these shape contracts now makes future mismatch errors easier to diagnose without guessing what a tensor contains.

Try it

  1. Read B, T, D and V from the declared teaching configuration.
  2. Create correctly typed ID and floating shape placeholders.
  3. Compare entry counts and final-axis meanings.
Python · run in order
B,T,D,V = (toy_config[name] for name in ["batch_size","context_length","hidden_width","vocab_size"])
id_slots = torch.zeros((B,T),dtype=torch.long)
hidden_slots = torch.zeros((B,T,D),dtype=torch.float32)
score_slots = torch.zeros((B,T,V),dtype=torch.float32)
names = ["Token ID slots","Hidden value slots","Vocabulary score slots"]
entry_counts = [tensor.numel() for tensor in [id_slots,hidden_slots,score_slots]]
fig, ax = plt.subplots(figsize=(8,3.5))
ax.bar(names,entry_counts,color=["#648da0","#547b92","#345e77"])
for index,count in enumerate(entry_counts):
    ax.text(index,count+2,str(count),ha="center")
ax.set(ylabel="Scalar entries",title="Calculated storage sizes for a tiny illustrative configuration",ylim=(0,110))
fig.tight_layout()

Read the result

The final axes refer to different things: learned-feature coordinates and candidate vocabulary entries. Equal tensor ranks do not make those axes interchangeable.

Change and compare

  • Double only the batch size and calculate which entry counts change.
  • Explain why a vocabulary ID's numeric value is not a confidence score.

Guided task 03

Parameters, predictions and updates

A trainable parameter is stored state that learning can change. An input is supplied data, and a prediction is a value computed from the current input and parameters. Running a prediction does not by itself perform a parameter update. Pretraining and later fine-tuning both update parameters, although they can use different data, objectives and selected subsets of weights.

Use a one-parameter numeric model as a small autograd warmup: prediction equals weight times input. The input is two, the target is three and the initial weight is one-half. Mark the weight with requires_grad so PyTorch records the operations needed to differentiate the squared error. Calling backward computes a gradient; the separate subtraction inside no_grad performs the update without building another differentiation graph. We then make a prediction under no_grad and verify that this prediction leaves the updated parameter unchanged. This toy model is not a language model and learns no vocabulary. It provides real gradients for a distinction that remains important when the parameter becomes a collection of transformer matrices. Later lessons add modules, optimizers and held-out evaluation rather than treating one smaller training error as evidence of useful language behavior.

Try it

  1. Compute a prediction and squared error for the stated scalar model.
  2. Differentiate, then apply one update with learning rate 0.1.
  3. Compare predictions before and after, and verify inference does not update the weight.
Python · run in order
weight = torch.tensor(0.5,requires_grad=True)
x = torch.tensor(2.0)
target = torch.tensor(3.0)
prediction_before = weight*x
loss = (prediction_before-target)**2
loss.backward()
gradient = float(weight.grad)
with torch.no_grad():
    weight -= 0.1*weight.grad
updated_weight = float(weight.detach())
with torch.no_grad():
    prediction_after = weight*x
unchanged_after_inference = float(weight.detach())
fig, ax = plt.subplots(figsize=(7,3.5))
ax.bar(["Before update","After update"],[float(prediction_before.detach()),float(prediction_after)],color=["#a78565","#447f9e"])
ax.axhline(float(target),color="black",linestyle="--",label="Target")
ax.set(ylabel="Scalar prediction",title="A real gradient update in a one-parameter numeric model",ylim=(0,3.5))
ax.legend()
fig.tight_layout()

Read the result

Backward produced a gradient, the update changed the parameter, and the final prediction only read it. These are distinct operations even when a training library packages them into a short loop.

Change and compare

  • Change the learning rate to zero and inspect the parameter update.
  • Derive the gradient of (2w-3) squared at w=0.5 by hand.

Guided task 04

Pretraining and task adaptation records

The development workflow connects architecture to data and objectives. General next-token pretraining can use text sequences without a separate human-written class label for every token. Classification adaptation uses an explicit label associated with an input. Instruction adaptation uses a request and a desired response, usually formatted into a sequence with an appropriate supervision policy.

Compare the fields of three small original record types: a library notice, a lost-and-found category example and a room-booking instruction pair. Compute a field-presence map from the actual dictionaries. This is a schema inspection, not a demonstration that storing a response has trained a model. The training code must still turn each record into inputs, supervised targets and a loss. Pretraining provides a general starting parameter state; task adaptation changes behavior through further learning, and inference uses the resulting state on new inputs. A model initialized from scratch has not received broad pretrained knowledge merely because it uses a transformer architecture. This course will build that mechanics at small scale and later distinguish tiny educational models from genuine pretrained checkpoints. Keep the origin and objective of every parameter state explicit.

Try it

  1. Construct one record for each stated learning setup.
  2. Inspect which data fields each setup requires.
  3. Keep data format separate from the learning code that would consume it.
Python · run in order
records = [
    {"kind":"pretraining text","text":"the library returns desk closes at six ."},
    {"kind":"classification","text":"a blue umbrella was found near the lift .","label":"lost-and-found"},
    {"kind":"instruction","instruction":"Rewrite this room request politely.","input":"give me room cedar","response":"Could I reserve room cedar, please?"}
]
fields = ["text","label","instruction","input","response"]
presence = np.array([[bool(row.get(field,"")) for field in fields] for row in records],dtype=int)
fig, ax = plt.subplots(figsize=(9,3.5))
ax.imshow(presence,cmap="Blues",vmin=0,vmax=1,aspect="auto")
ax.set_xticks(range(len(fields)),fields)
ax.set_yticks(range(3),[row["kind"] for row in records])
for row in range(3):
    for column in range(len(fields)):
        ax.text(column,row,"present" if presence[row,column] else "-",ha="center",va="center",fontsize=9,color="white" if presence[row,column] else "black")
ax.set_title("Fields present in three constructed training-record formats")
fig.tight_layout()

Read the result

The required supervision differs across these records. Field presence says what data is available, not whether a model has learned the intended behavior or will perform well on unseen requests.

Change and compare

  • Add a classification example without a label and identify the missing supervision.
  • Explain why a response field alone does not specify which prompt or padding tokens contribute to a training loss.

Guided task 05

Independent documents before training examples

A text collection can contain several versions of the same underlying notice. These rows are not independent evidence simply because their strings differ. If a long document later produces overlapping training windows, those windows are also related. Split trustworthy source groups before creating windows, fitting data-derived preprocessing or selecting settings.

The setup has two versions of each of six notices. Shuffle the sorted group IDs with local seed 102, assign four groups to training, one to validation and one to test, and let every version inherit its group's assignment. Plot both document-row counts and independent-group counts. Training is used for parameter updates, validation supports development choices and the final test partition is reserved for the final evaluation plan. This tiny split is only a mechanics example; six notices do not establish that an evaluation covers real language variation. Duplicate or related sources may need grouping beyond an obvious document ID. Make that policy explicit before measuring performance, because a lower error on related versions in another partition can exaggerate how well a model handles genuinely new material.

Try it

  1. Resolve the six notice groups before assigning individual rows.
  2. Create a reproducible 4/1/1 group split.
  3. Compare row counts with group counts and verify inheritance.
Python · run in order
groups = sorted({row["group"] for row in notices})
ordered = np.random.default_rng(102).permutation(groups)
group_split = {str(group):split for group,split in zip(ordered,["train"]*4+["validation","test"])}
row_split = {row["id"]:group_split[row["group"]] for row in notices}
split_names = ["train","validation","test"]
row_counts = [sum(split==name for split in row_split.values()) for name in split_names]
group_counts = [sum(split==name for split in group_split.values()) for name in split_names]
positions = np.arange(3)
fig, ax = plt.subplots(figsize=(8,3.5))
ax.bar(positions-0.18,row_counts,width=0.36,label="Notice versions")
ax.bar(positions+0.18,group_counts,width=0.36,label="Independent groups")
ax.set_xticks(positions,split_names)
ax.set(ylabel="Count",title="Split source groups before making related windows")
ax.legend()
fig.tight_layout()

Read the result

Eight training rows represent four independent notices in this fixture. The split assignment belongs to the source group and must also be inherited by any later windows made from those versions.

  • Explain why shuffling overlapping windows cannot repair a split that already shares their source document.

Guided task 06

Parameter storage and training overhead

A parameter count is not a complete memory budget. Storing a tensor requires its number of elements multiplied by bytes per element. A float32 value uses four bytes and a float16 value uses two. Those facts describe numeric storage, not a guarantee that an entire training run uses exactly half the memory after a dtype change.

Allocate a small 6000-by-64 table in both dtypes and calculate its parameter-storage bytes without using the uninitialized values. Then build an illustrative float32 training-state estimate containing the weights, one equally sized gradient array and two equally sized optimizer-moment arrays. This estimate excludes activations, temporary workspaces, other model tensors and implementation overhead. Mixed-precision training can retain additional higher-precision copies, while inference can require caches and other state. The purpose is to separate a measurable component from an unsupported total-RAM promise. Report binary mebibytes using division by 1024 squared, and label the estimate's assumptions. Later model-assembly and checkpoint labs will count complete parameter collections and distinguish tied weights from separate storage. Here even one table is enough to show why weight bytes alone cannot predict a training machine's requirements.

Try it

  1. Calculate storage from tensor element counts and element sizes.
  2. Compare two dtypes for the same table shape.
  3. Estimate explicitly named float32 training-state components.
Python · run in order
table32 = torch.empty((6000,64),dtype=torch.float32)
table16 = torch.empty((6000,64),dtype=torch.float16)
bytes32 = table32.numel()*table32.element_size()
bytes16 = table16.numel()*table16.element_size()
components = {"weights":bytes32,"gradients":bytes32,"two moments":2*bytes32}
fig, axes = plt.subplots(1,2,figsize=(10,3.5))
axes[0].bar(["float32","float16"],np.array([bytes32,bytes16])/1024**2,color="#447f9e")
axes[0].set(ylabel="MiB",title="Parameter table only")
axes[1].bar(list(components),np.array(list(components.values()))/1024**2,color="#947454")
axes[1].set(ylabel="MiB",title="Illustrative float32 training-state components")
fig.tight_layout()

Read the result

The table has the same number of parameters in both dtypes. The second panel names included components rather than implying that their sum is the process's full memory footprint.

Change and compare

  • Add a hypothetical equally sized master-weight copy and recalculate the subtotal.
  • List two memory consumers absent from the plotted training-state estimate.

Guided task 07

Context length and pairwise work

Transformer attention relates positions to other positions. A straightforward dense score matrix for a sequence of length T has T squared entries for one head and one sequence. A causal permission pattern retains T times (T plus one) divided by two allowed entries, but applying that mask does not automatically shrink the dense matrix's allocated shape.

Calculate these counts for several context lengths and plot their growth. The chart describes a simple dense representation, not a wall-clock benchmark or a claim about every optimized attention implementation. Doubling context length multiplies the dense pair-slot count by four. Other parts of a model can scale differently, and hardware kernels, batching, memory layout and precision affect actual performance. Context length also changes what information a request can include, so it is both a modeling choice and a resource choice. Keep the permitted-connection count distinct from allocated storage and from executed hardware operations. Later attention labs will construct small real score tensors, while more advanced implementations can avoid materializing the entire dense matrix. This preliminary calculation helps identify which assumptions must be stated when comparing resource claims.

Try it

  1. Calculate dense and causally permitted pair counts.
  2. Compare them as context length increases.
  3. Keep pair-slot accounting separate from measured runtime.
Python · run in order
lengths = np.array([16,32,64,128])
dense_pairs = lengths**2
causal_pairs = lengths*(lengths+1)//2
fig, ax = plt.subplots(figsize=(8,3.5))
ax.plot(lengths,dense_pairs,"o-",label="Dense matrix slots")
ax.plot(lengths,causal_pairs,"s-",label="Permitted causal pairs")
ax.set(xlabel="Context length T",ylabel="Position pairs",title="Calculated counts for one sequence and one attention head")
ax.legend()
fig.tight_layout()

Read the result

The causal count is smaller than the dense slot count, but both grow quadratically in this representation. A mask's zeroed entries alone do not establish memory savings in an implementation.

Change and compare

  • Calculate the two counts for T=1 and explain why they agree.
  • Identify what additional measurements would be required to make a runtime comparison.

Guided task 08

Reproducible from-scratch experiments

A seed controls a random-number stream; it is one part of an experiment record. Reproducing an experiment also requires its data identities and splits, tokenization rules, model configuration, dtype, software versions and training procedure. A seed alone cannot make a different architecture or reordered data pipeline equivalent.

Create three small random tensors with local PyTorch generators. Two use seed 102 and one uses seed 103. These are illustrative initial parameter values, not pretrained weights and not learned language features. Compare them on shared heatmap limits and build a compact metadata record describing the experiment's CPU, dtype, configuration and source IDs. Local generators make the random dependency explicit and avoid relying on unrelated notebook calls that may have advanced a global stream. Matching initial values does not guarantee identical results across every hardware platform or library release; deterministic execution settings and algorithm choices can matter as well. The practical habit is to record what was done and verify the behavior that matters, rather than interpreting a familiar-looking loss curve as sufficient evidence of reproducibility.

Try it

  1. Create two replayed initializations and one with a different seed.
  2. Display their actual values on a common colour scale.
  3. Record configuration, data IDs, dtype, device and software version.
Python · run in order
initial_a = torch.randn((3,4),generator=torch.Generator().manual_seed(102))
initial_b = torch.randn((3,4),generator=torch.Generator().manual_seed(102))
initial_c = torch.randn((3,4),generator=torch.Generator().manual_seed(103))
run_record = {"seed":102,"device":"cpu","dtype":"float32","initialization":"from scratch","torch_version":torch.__version__,"config":dict(toy_config),"source_ids":sorted(row["id"] for row in notices)}
limit = max(float(tensor.abs().max()) for tensor in [initial_a,initial_b,initial_c])
fig, axes = plt.subplots(1,3,figsize=(10,3.5),constrained_layout=True)
for ax,tensor,title in zip(axes,[initial_a,initial_b,initial_c],["Run A: seed 102","Replay B: seed 102","Run C: seed 103"]):
    im = ax.imshow(tensor.numpy(),cmap="coolwarm",vmin=-limit,vmax=limit)
    ax.set(xlabel="Feature index",ylabel="Row",title=title)
fig.colorbar(im,ax=axes,label="Initial random value",shrink=0.8)

Read the result

The first two arrays match because their explicit generators replay the same stream. Nothing in these random values demonstrates a pretrained capability, and the record makes that origin explicit.

Change and compare

  • Advance one generator before drawing and inspect why the same seed label is not enough without the call sequence.
  • Add the exact data-group assignment to the metadata needed for a later training run.
