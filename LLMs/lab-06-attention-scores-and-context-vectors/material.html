Attention Scores and Context Vectors

MaterialPracticeQuiz

Build attention one operation at a time and inspect where every output value comes from. Use short everyday requests to connect dot products, normalized weights and context vectors.

What you will learn

  • Compute one-query and all-query dot-product attention.
  • Distinguish scores, normalized weights and weighted feature vectors.
  • Test numerical and shape invariants without interpreting weights as factual certainty.
  • Explain how other positions, ordering information and repeated sources affect the result.

Before this lab: Use token and position vectors, matrix multiplication and basic PyTorch tensor indexing.

Guided task 01

One query and its dot-product scores

A request contains several token vectors, but a fixed token lookup does not combine them. Attention constructs a new vector for a selected position by mixing information from source positions. Begin with the simplest scoring rule: use the selected input vector itself as a query and take its dot product with every input row. Later labs introduce separately learned query, key and value projections.

The fixture represents bring, the, blue, mug and a full stop with three handcrafted features each. These numbers illustrate arithmetic rather than learned word meaning. For the mug query, multiply matching features and add them to obtain one score per source position. A negative score is valid because signed features can contribute opposing terms. A score is not yet a normalized weight or a probability of a correct next word.

The loop and matrix-vector product perform the same calculation. features @ query has shape (5,), with one result for each source row. The query also scores against itself. Nothing here prevents looking at later positions: this is unrestricted, untrained attention used to study the mechanism, not a causal next-token model ready for generation.

Try it

  1. Choose the mug row as the query.
  2. Compute every source score with a loop and with matrix multiplication.
  3. Plot the scores in the original source-token order.
Python · run in order
query_index = 3
query = features[query_index]
loop_scores = torch.stack([torch.dot(query, row) for row in features])
scores = features @ query
fig, ax = plt.subplots(figsize=(8, 3.8), constrained_layout=True)
ax.bar(labels, scores.numpy(), color=["#e9c46a" if i == query_index else "#457b9d" for i in range(len(labels))])
ax.axhline(0, color="#555555", linewidth=0.8)
ax.set_ylabel("Unnormalized dot-product score")
ax.set_title("One mug query compared with every source position")

Read the result

The self-score is one entry among all source scores. Its size depends on the vector's squared length; high dot products can reflect feature magnitude as well as alignment. None of these handcrafted scores demonstrates language understanding.

Change and compare

  • Choose another query row and calculate one score by hand.
  • Multiply only the query by two and inspect how all scores change.

Guided task 02

From scores to normalized weights

To make a weighted average, we need nonnegative coefficients whose sum is one. Dividing arbitrary scores by their sum does not guarantee that property. The mug example contains a negative score, so direct division leaves a negative coefficient. A row of scores might even sum to zero, making that division undefined.

Softmax handles signed finite scores by exponentiating them and normalizing the resulting positive numbers. Its outputs sum to one along the chosen axis, up to floating-point rounding. torch.softmax(scores, dim=0) normalizes the five source positions for this single query. Larger scores receive larger weights, while equal scores receive equal weights. The operation compares scores within the current collection; adding or removing sources can change every weight.

These attention weights describe how feature rows will be mixed. They are not next-token vocabulary probabilities and do not measure whether a statement is true. The source positions form their normalization domain. A later language-model output layer has a different domain: vocabulary entries. Keeping those domains distinct prevents a visually convincing attention chart from being mistaken for an answer-confidence chart.

Try it

  1. Compute direct division only as a diagnostic comparison.
  2. Apply softmax to the same score vector across source positions.
  3. Compare signs, totals and the ordering of the resulting coefficients.
Python · run in order
scores = features @ features[3]
divided = scores / scores.sum()
weights = torch.softmax(scores, dim=0)
fig, axes = plt.subplots(1, 2, figsize=(10, 3.8), constrained_layout=True)
axes[0].bar(labels, divided.numpy(), color="#e76f51")
axes[0].axhline(0, color="#555555", linewidth=0.8)
axes[0].set_title("Scores divided by their sum")
axes[0].set_ylabel("Coefficient (may be negative)")
axes[1].bar(labels, weights.numpy(), color="#2a9d8f")
axes[1].set_title("Softmax over source positions")
axes[1].set_ylabel("Attention weight")

Read the result

The direct coefficients sum to one but include a negative value, so the sum test alone is insufficient. Softmax supplies both nonnegativity and normalization, with the highest weight attached to the highest score.

Change and compare

  • Set every score to the same finite value and predict the weights.
  • Append one additional source score and inspect how existing weights are renormalized.

Guided task 03

A context vector is a weighted feature sum

Once one query's weights are available, multiply each source vector by its corresponding coefficient and add the resulting vectors. The answer has the original feature width, not the number of source tokens. Here five three-feature rows become one three-feature context vector. This gives the selected position a mixture drawn from the full request.

The expression weights[:, None] inserts a size-one feature axis. Multiplication then broadcasts each scalar across all features of its own source row. Summing those contributions along the source axis gives the same result as the vector-matrix product weights @ features. Neither operation chooses a single winning token. Even sources with small weights can contribute to every output feature.

Because the weights are nonnegative and sum to one, each output coordinate lies between the smallest and largest source coordinate for that feature, within rounding tolerance. This is a useful arithmetic check. The combined vector need not equal any input row or correspond directly to a vocabulary token. Decoding it by choosing the nearest handcrafted row would add an unsupported rule that this attention operation does not define.

Try it

  1. Compute softmax weights for the mug query.
  2. Build and display the contribution from each source position.
  3. Sum contributions and compare the context with direct matrix multiplication.
Python · run in order
weights = torch.softmax(features @ features[3], dim=0)
contributions = weights[:, None] * features
context = contributions.sum(dim=0)
by_product = weights @ features
fig, axes = plt.subplots(1, 2, figsize=(9, 4), constrained_layout=True)
image = axes[0].imshow(contributions.numpy(), cmap="coolwarm", aspect="auto")
axes[0].set_yticks(range(len(labels)), labels)
axes[0].set_xticks(range(3), ["f0", "f1", "f2"])
axes[0].set_title("Each weighted source contribution")
fig.colorbar(image, ax=axes[0], label="Weighted feature value")
axes[1].bar(["f0", "f1", "f2"], context.numpy(), color="#457b9d")
axes[1].set_ylabel("Context feature value")
axes[1].set_title("Sum across source positions")

Read the result

The heatmap shows individual signed contributions, while the bar chart shows their featurewise sums. A positive weight can multiply a negative source feature, so a negative contribution does not mean an invalid attention weight.

Change and compare

  • Use uniform weights and compare the result with the mean source vector.
  • Temporarily use a one-hot weight vector to verify that it selects one source row.

Guided task 04

All queries in one matrix calculation

The single-query computation can be performed for every token at once. For an input matrix X with shape (T, D), X @ X.T produces a (T, T) score matrix. Row i contains the scores from query position i to all source positions. Column j identifies the source whose vector may contribute. Labeling both axes avoids confusing query and source roles.

Normalize each row with torch.softmax(scores, dim=-1). The last axis represents source positions, so each query receives its own set of weights summing to one. Multiplying this weight matrix by X produces a (T, D) context matrix. Each row now contains the independently computed mixture for its query position; no Python loop is required for the arithmetic.

The raw score matrix in this unprojected example is symmetric because dot products are symmetric. The normalized weight matrix generally is not: different rows have different softmax denominators. Column totals also need not equal one. This distinction is important when auditing an attention heatmap. Symmetric-looking relationships are not a requirement for normalized attention weights, and all-position access remains unrestricted here.

Try it

  1. Form the query-by-source score matrix.
  2. Normalize across each query's source columns.
  3. Calculate every context vector and compare one row with the single-query method.
Python · run in order
score_matrix = features @ features.T
attention = torch.softmax(score_matrix, dim=-1)
contexts = attention @ features
fig, axes = plt.subplots(1, 3, figsize=(12, 4), constrained_layout=True)
for ax, values, title, cmap in [(axes[0], score_matrix, "Query-source scores", "coolwarm"), (axes[1], attention, "Row-normalized weights", "viridis"), (axes[2], contexts, "Context vectors", "coolwarm")]:
    image = ax.imshow(values.numpy(), cmap=cmap, aspect="auto")
    ax.set_yticks(range(len(labels)), labels)
    ax.set_ylabel("Query position")
    if values.shape[1] == len(labels):
        ax.set_xticks(range(len(labels)), labels, rotation=45, ha="right")
        ax.set_xlabel("Source position")
    else:
        ax.set_xticks(range(3), ["f0", "f1", "f2"])
        ax.set_xlabel("Feature")
    ax.set_title(title)
    fig.colorbar(image, ax=ax, label="Weight" if ax is axes[1] else "Value")

Read the result

Every attention row sums to one, while its columns need not. The mug context agrees with the earlier calculation. The final matrix has one row per query and one column per feature, not one column per vocabulary entry.

Change and compare

  • Normalize the score matrix along axis zero and inspect row sums.
  • Duplicate the single-query calculation for another row to check the matrix result.

Guided task 05

Stable softmax and score shifts

Adding the same finite constant to every score in one row does not change its softmax weights. In the exponential formula, that addition multiplies every numerator and the denominator by the same factor, which cancels. This invariance lets us subtract the row's maximum score before exponentiation. The largest adjusted score becomes zero and no adjusted score is positive.

The example uses deliberately large scores to expose the numerical issue. Direct exponentiation of scores near 1000 overflows even in float64, although their differences are small and their normalized weights are perfectly well defined. Computing exponentials after subtracting the maximum avoids that overflow for these inputs. Dividing by the sum of those adjusted exponentials then matches torch.softmax.

Use the library operation for normal model code; the manual calculation here explains its stable form. This transformation does not correct invalid inputs such as NaN, and adding a constant is different from multiplying scores by a constant. Multiplication changes score differences and generally changes the weight distribution. Neither change should be confused with scaling the resulting context vector after weighting.

Try it

  1. Inspect large finite scores and whether their direct exponentials remain finite.
  2. Subtract the maximum, exponentiate and normalize manually.
  3. Compare with library softmax and with a constant-shifted score row.
Python · run in order
large_scores = torch.tensor([1000.0, 1001.0, 999.0], dtype=torch.float64)
raw_exponentials_finite = bool(torch.isfinite(torch.exp(large_scores)).all())
centered = large_scores - large_scores.max()
terms = torch.exp(centered)
manual_weights = terms / terms.sum()
library_weights = torch.softmax(large_scores, dim=0)
shifted_weights = torch.softmax(large_scores + 250.0, dim=0)
fig, axes = plt.subplots(1, 2, figsize=(9, 3.8), constrained_layout=True)
axes[0].bar(["source 0", "source 1", "source 2"], centered.numpy(), color="#457b9d")
axes[0].set_title("Scores after subtracting the maximum")
axes[0].set_ylabel("Adjusted score")
x = np.arange(3)
axes[1].bar(x - 0.18, manual_weights.numpy(), width=0.36, label="Manual stable form")
axes[1].bar(x + 0.18, library_weights.numpy(), width=0.36, label="torch.softmax")
axes[1].set_xticks(x, ["source 0", "source 1", "source 2"])
axes[1].set_ylabel("Normalized weight")
axes[1].set_title("Finite weights despite large raw scores")
axes[1].legend()

Read the result

The adjusted scores preserve all pairwise differences, and both computations agree on the weights. The large raw exponentials fail the finite-value check, but that failure does not imply the normalized problem itself is undefined.

Change and compare

  • Add another common constant to all scores in the row and compare weights.
  • Multiply the score differences by two and compare with the unchanged constant-shift case.

Guided task 06

Changing a neighboring source

A context vector depends on the source feature rows as well as the attention weights. Change only the blue row while keeping the mug query unchanged. There are two useful experiments: reuse the original weights with the edited sources, or recompute both scores and weights from the edited sources. These isolate a direct feature contribution from the full simplified-attention response.

With fixed weights, the context change has a simple form. Only one source row changed, so the output difference equals that row's weight multiplied by its feature change. Recomputing attention adds another effect: the edited source receives a different dot-product score, and the shared softmax denominator can change the weights on every source, including unchanged ones.

This experiment demonstrates contextual dependence inside the mathematical operation. It does not establish that a particular feature represents color, or that the largest weight explains a language model's final answer. Our features remain handcrafted. Attention weights alone omit the source-vector values and all subsequent computation. Inspecting both ingredients gives a more faithful account of what this small module actually calculates.

Try it

  1. Save the baseline mug weights and context.
  2. Edit the blue source by adding [0.4,-0.3,0.2].
  3. Compare the fixed-weight edit with a complete recomputation.
Python · run in order
baseline_weights = torch.softmax(features @ features[3], dim=0)
baseline_context = baseline_weights @ features
delta = torch.tensor([0.4, -0.3, 0.2])
edited = features.clone()
edited[2] += delta
fixed_context = baseline_weights @ edited
edited_weights = torch.softmax(edited @ edited[3], dim=0)
edited_context = edited_weights @ edited
fig, axes = plt.subplots(1, 2, figsize=(10, 4), constrained_layout=True)
x = np.arange(len(labels))
axes[0].bar(x - 0.18, baseline_weights.numpy(), width=0.36, label="Baseline")
axes[0].bar(x + 0.18, edited_weights.numpy(), width=0.36, label="Recomputed")
axes[0].set_xticks(x, labels)
axes[0].set_ylabel("Attention weight")
axes[0].set_title("A source edit can change every weight")
axes[0].legend()
changes = torch.stack([fixed_context - baseline_context, edited_context - baseline_context])
image = axes[1].imshow(changes.numpy(), cmap="coolwarm", aspect="auto")
axes[1].set_yticks([0, 1], ["Keep original weights", "Recompute weights"])
axes[1].set_xticks(range(3), ["f0", "f1", "f2"])
axes[1].set_title("Context change from the source edit")
fig.colorbar(image, ax=axes[1], label="Feature change")

Read the result

The fixed-weight change follows one weighted feature difference exactly. Full recomputation also redistributes weights. A source can influence the output through its content and through the normalization shared with other sources.

Change and compare

  • Edit a different source row and repeat the two comparisons.
  • Use a zero feature change and confirm that both output changes disappear.

Guided task 07

Order information and permutation behavior

Unrestricted attention computed only from token features does not know which physical position is first or last. If the input rows are permuted, the score rows and columns are permuted consistently, and the output context rows follow the same permutation. After undoing the row permutation, the original contexts are recovered. This property is called permutation equivariance: outputs move with the inputs rather than remaining fixed in their old positions.

A language request often needs order information. Add a separate position vector at each current position, as in the previous lab. Now move the token rows while keeping the position table attached to its positions. The moved tokens receive different position contributions, so merely undoing the output permutation generally does not reproduce the earlier contexts. The fixture makes that contrast visible.

This experiment does not prove that adding positions teaches grammar; no model is trained here. It identifies information the computation can distinguish. Nor should equivariance be described as identical output order for reordered input. The first comparison explicitly restores the original token order before subtracting results. Keeping that alignment step visible prevents a row-order difference from being mistaken for a change in contextual values.

Try it

  1. Implement the three-operation simplified attention function.
  2. Swap bring and mug, then align the output rows back to the original token order.
  3. Repeat with fixed position features and compare aligned differences.
Python · run in order
def simple_context(x):
    return torch.softmax(x @ x.T, dim=-1) @ x
permutation = torch.tensor([3, 1, 2, 0, 4])
inverse = torch.argsort(permutation)
original_contexts = simple_context(features)
permuted_contexts = simple_context(features[permutation])
without_position_change = permuted_contexts[inverse] - original_contexts
positioned_original = simple_context(features + position_features)
positioned_permuted = simple_context(features[permutation] + position_features)
with_position_change = positioned_permuted[inverse] - positioned_original
fig, axes = plt.subplots(1, 2, figsize=(9, 4), constrained_layout=True)
limit = max(float(with_position_change.abs().max()), 0.01)
for ax, values, title in [(axes[0], without_position_change, "Aligned difference: token features only"), (axes[1], with_position_change, "Aligned difference: fixed positions added")]:
    image = ax.imshow(values.numpy(), cmap="coolwarm", vmin=-limit, vmax=limit, aspect="auto")
    ax.set_yticks(range(len(labels)), labels)
    ax.set_xticks(range(3), ["f0", "f1", "f2"])
    ax.set_title(title)
fig.colorbar(image, ax=axes, label="Aligned context feature difference")

Read the result

The content-only differences are zero within floating-point tolerance after realignment. The position-aware case differs because moved tokens receive new positional contributions, not because the dot-product formula itself changed.

Change and compare

  • Try another permutation and verify the content-only alignment result.
  • Permute both token and position rows together and compare with keeping positions fixed.

Guided task 08

Repeated source rows change total attention mass

A repeated source is still a separate position in an attention calculation. To isolate this effect, hold the mug query fixed and append an exact copy of the blue source vector. Both blue rows receive the same dot-product score and therefore the same individual softmax weight. However, together they receive more total weight than the single original blue row did.

The reason is normalization over positions. Copying a source adds another equal exponential term to the denominator and another contribution for that same feature vector. Other positions consequently receive smaller weights. The context generally changes even though no new feature value has been introduced. This behavior is different from converting the source rows to a set, which would discard multiplicity.

Real requests may contain repeated words, and learned representations can distinguish their positions or contexts. Our controlled example deliberately duplicates the entire feature row and omits position information so the normalization mechanism is clear. It also shows why an attention weight depends on the available source collection: a coefficient should not be compared across different contexts as though it were an intrinsic property of a word.

Try it

  1. Compute baseline weights for a fixed mug query.
  2. Append a duplicate blue row without changing the query.
  3. Compare combined blue weight and the resulting context features.
Python · run in order
query = features[3].clone()
original_weights = torch.softmax(features @ query, dim=0)
duplicated_sources = torch.cat([features, features[2:3]], dim=0)
duplicate_weights = torch.softmax(duplicated_sources @ query, dim=0)
blue_mass_before = original_weights[2]
blue_mass_after = duplicate_weights[2] + duplicate_weights[-1]
original_context = original_weights @ features
duplicate_context = duplicate_weights @ duplicated_sources
fig, axes = plt.subplots(1, 2, figsize=(9, 3.8), constrained_layout=True)
axes[0].bar(["One blue row", "Two blue rows"], [blue_mass_before.item(), blue_mass_after.item()], color=["#457b9d", "#2a9d8f"])
axes[0].set_ylabel("Combined weight on blue features")
axes[0].set_ylim(0, 1)
axes[0].set_title("Multiplicity changes normalized mass")
x = np.arange(3)
axes[1].bar(x - 0.18, original_context.numpy(), width=0.36, label="Original sources")
axes[1].bar(x + 0.18, duplicate_context.numpy(), width=0.36, label="One source duplicated")
axes[1].set_xticks(x, ["f0", "f1", "f2"])
axes[1].set_ylabel("Context feature value")
axes[1].set_title("Same available values, different mixture")
axes[1].legend()

Read the result

The two identical blue rows split equal individual weights, and their combined share increases. If every source vector were identical, changing their number would leave the weighted context unchanged even though individual weights changed.

Change and compare

  • Duplicate every source row equally and compare the combined contribution of each original row.
  • Try identical source vectors and verify the special case where the context remains the same.
