Batches and Optimization

MaterialPracticeQuiz

Make the training loop less mysterious by tracing the examples and updates it uses. Small meal-preparation records let you inspect every quantity before fitting a model.

What you will learn

  • Keep inputs and targets paired while batching and shuffling.
  • Aggregate losses correctly when batch lengths differ.
  • Connect gradients and learning rates to parameter updates.
  • Compare optimizer experiments without confusing epochs and updates.

Python · shared setup
import tensorflow as tf
import keras
import numpy as np
import matplotlib.pyplot as plt
keras.utils.set_random_seed(106)
rng = np.random.default_rng(106)
# Invented meal-preparation records: portions and preparation minutes.
portions = rng.integers(1, 11, 96).astype('float32')
minutes = (8 + 3 * portions + rng.normal(0, 1.5, 96)).astype('float32')
order = rng.permutation(96)
train_ids, val_ids, test_ids = order[:64], order[64:80], order[80:]
# Fixed unit conversions, not statistics learned from held-out records.
x_train = (portions[train_ids, None] / 10).astype('float32')
y_train = (minutes[train_ids, None] / 60).astype('float32')
x_val = (portions[val_ids, None] / 10).astype('float32')
y_val = (minutes[val_ids, None] / 60).astype('float32')

def batches(x, y, batch_size=16, shuffle=False):
    ds = tf.data.Dataset.from_tensor_slices((x, y))
    if shuffle:
        ds = ds.shuffle(len(x), seed=123, reshuffle_each_iteration=True)
    options = tf.data.Options()
    options.threading.private_threadpool_size = 1
    options.threading.max_intra_op_parallelism = 1
    return ds.batch(batch_size).with_options(options)

Guided task 01

Mini-batches and the final partial group

A mini-batch is a group of paired examples used for one loss and usually one optimizer update. It is not a new train/validation split. The setup already assigned record IDs to disjoint sets before any training. Here the training set contains sixty-four invented kitchen records, and each row still represents one portion count with its preparation time. The plotted units are restored for readability even though the arrays use fixed normalized units.

A requested batch size is a maximum, not a promise that every group has that many rows. Eighteen-row groups leave a shorter final group because the helper does not discard remaining examples. Keeping that group means every training record participates in the pass. Count the actual rows instead of inferring them from the requested size. An epoch normally means one pass through this finite training dataset, while an update happens within the pass. These two counts answer different questions and will matter when comparing experiments later.

Try it

  1. Create unshuffled batches of eighteen training records.
  2. Read the size of every returned group and verify that their total covers the training set.
  3. Plot the training and validation records in portions and minutes.
Python · run in order
sizes = [int(xb.shape[0]) for xb, yb in batches(x_train, y_train, 18)]
print('Batch sizes:', sizes, 'Total:', sum(sizes))
fig, ax = plt.subplots(figsize=(6, 4))
ax.scatter(x_train[:, 0] * 10, y_train[:, 0] * 60, label='training', alpha=0.7)
ax.scatter(x_val[:, 0] * 10, y_val[:, 0] * 60, label='validation', marker='x')
ax.set(xlabel='Portions', ylabel='Preparation minutes', title='Invented kitchen records')
ax.legend()
fig.tight_layout()

Read the result

The points show the supplied records, while the printed sizes describe how the training records are grouped. A short final batch is expected and does not indicate missing data.

  • Try a batch size that divides sixty-four exactly.
  • Explain why regrouping training records must not move validation IDs into training.

Guided task 02

Paired shuffling and row identity

Shuffling changes order, not membership. A learning algorithm can otherwise encounter a long run of similar records before seeing a different part of the input range. Random order is often useful for ordinary independent records, although it is not permission to shuffle away meaningful sequence structure in a time-dependent problem. This fixture treats the kitchen records as separate examples.

The same permutation must index both input and target arrays. Shuffling the two arrays independently would silently teach preparation times against the wrong portion counts. Attach a record ID when inspecting a pipeline so that this mistake is visible. The code makes a local permutation for a small inspection and compares original and shuffled positions. The helper used for fitting can reshuffle its paired dataset between epochs. A fixed seed supports repeatable experiments, but it does not make every repeated iteration use identical order when reshuffling is explicitly enabled. Preserve the pair, the split membership, and the stated order policy as three separate invariants.

Try it

  1. Choose one permutation of the training row positions.
  2. Apply it to both arrays and retain the reordered record IDs.
  3. Plot the first twelve input values before and after the permutation.
Python · run in order
permutation = np.random.default_rng(606).permutation(len(x_train))
shuffled_x = x_train[permutation]
shuffled_y = y_train[permutation]
shuffled_ids = train_ids[permutation]
fig, ax = plt.subplots(figsize=(6, 4))
ax.plot(np.arange(12), x_train[:12, 0] * 10, 'o-', label='original order')
ax.plot(np.arange(12), shuffled_x[:12, 0] * 10, 's-', label='paired shuffle')
ax.set(xlabel='Position in inspection', ylabel='Portions', title='Order changes; records stay paired')
ax.legend()
fig.tight_layout()

Read the result

The two lines are order inspections, not time series or learning curves. Every shuffled target still comes from the same original record as its shuffled input.

  • Identify what must stay true even when the plotted order changes.

Guided task 03

Example-weighted loss aggregation

A mean loss describes examples only when each example receives the intended weight. If the final batch is shorter, simply averaging batch means gives that batch the same influence as a full batch. To recover the mean across all examples, multiply each batch mean by its actual count, add these totals, then divide by the total number of examples. This is bookkeeping about a fixed set of losses, before any optimizer changes the model.

The toy vector below deliberately has an uneven final group and different losses in that group. It makes the arithmetic visible without relying on a trained model. The batch means answer local questions, while the weighted result answers the dataset-wide question. During real training, predictions can change between batches, so a running training loss and a fresh evaluation of the final model need not be identical even with correct weighting. First separate that model-change issue from the simpler counting issue. Recording both counts and sums is a reliable way to combine partial reports.

Try it

  1. Group the supplied per-example squared errors in groups of three.
  2. Calculate the mean and count of each group.
  3. Compare the example-weighted aggregate with the direct full-vector mean.
Python · run in order
errors = np.array([1, 1, 1, 4, 4, 4, 16, 16], dtype='float32')
groups = [errors[i:i+3] for i in range(0, len(errors), 3)]
means = np.array([g.mean() for g in groups])
counts = np.array([len(g) for g in groups])
weighted = np.sum(means * counts) / counts.sum()
print('Weighted:', weighted, 'Direct:', errors.mean())
fig, ax = plt.subplots(figsize=(6, 4))
ax.bar(['first 3', 'next 3', 'last 2'], means)
ax.axhline(weighted, color='black', linestyle='--', label='all-example mean')
ax.set(ylabel='Squared error', title='Unequal batch lengths require weights')
ax.legend()
fig.tight_layout()

Read the result

The aggregate matches the direct mean. Its position need not be halfway between the tallest and shortest bars because the groups contain different numbers of examples.

Change and compare

  • Add one more error equal to sixteen and recompute.
  • Compare the weighted result with an unweighted mean of the three bars.

Guided task 04

Gradient direction and one SGD update

Gradient descent changes a parameter in the direction opposite the gradient. The gradient measures how the loss changes locally when the parameter changes; it is not the loss value itself. A learning rate scales the proposed change. In this deliberately small example there is only one weight, no bias, and three exact pairs with target equal to twice the input. That simplicity lets the tape result be checked by ordinary arithmetic.

GradientTape records the forward calculation performed inside its context. The weight is a TensorFlow variable so the gradient can be taken with respect to it. After the loss is computed, the optimizer receives a gradient-variable pair and applies one update. The new predictions are drawn separately from the old ones. A single favorable update does not establish convergence, and the same learning rate need not work with a different input scale. Always inspect the units and the magnitude of the gradient before attributing a large jump to an optimizer defect.

Try it

  1. Create the exact three-pair fixture and a scalar weight initially zero.
  2. Record mean squared error in GradientTape and compute its gradient.
  3. Apply one SGD update at learning rate 0.1 and compare predictions.
Python · run in order
small_x = tf.constant([0.0, 0.5, 1.0])
small_y = 2 * small_x
weight = tf.Variable(0.0)
with tf.GradientTape() as tape:
    loss = tf.reduce_mean(tf.square(weight * small_x - small_y))
gradient = tape.gradient(loss, weight)
optimizer = keras.optimizers.SGD(learning_rate=0.1)
optimizer.apply_gradients([(gradient, weight)])
print('Gradient:', float(gradient), 'Updated weight:', float(weight))
fig, ax = plt.subplots(figsize=(6, 4))
ax.plot(small_x.numpy(), small_y.numpy(), 'o-', label='target')
ax.plot(small_x.numpy(), np.zeros(3), '--', label='before update')
ax.plot(small_x.numpy(), (weight * small_x).numpy(), 's-', label='after one update')
ax.set(xlabel='Scaled input', ylabel='Scaled output', title='One gradient-driven change')
ax.legend()
fig.tight_layout()

Read the result

The numerical gradient determines the direction and size of this one change. Compare the updated weight with the target slope, rather than expecting one step to solve the entire problem.

Change and compare

  • Repeat from zero with half the learning rate.
  • Explain why changing the starting weight also changes the gradient.

Guided task 05

Learning-rate sensitivity

A learning rate that is too large can repeatedly cross a minimum and increase the loss. A very small rate can move safely but slowly. To isolate this effect, use a known one-dimensional bowl whose minimum is at weight one. The code calculates its exact gradient, so neither minibatch randomness nor a neural architecture can explain differences between the two traces.

Both runs begin at weight four and take the same number of updates. The only changed setting is the learning rate. The plotted loss uses a logarithmic vertical scale because one trace can cover a much larger range. This scale changes the display, not the values being optimized. A rate that works on this particular quadratic is not a universal recommendation for kitchen data or image classifiers. Curvature, feature scale, batch noise and optimizer state all affect useful settings. Use controlled experiments to diagnose optimization before adding model complexity, and stop interpreting a diverging curve as ordinary measurement noise.

Try it

  1. Follow the exact gradient of (weight - 1) squared from the same starting weight.
  2. Use learning rates 0.1 and 1.1 for twelve updates each.
  3. Plot the losses on one logarithmic axis.
Python · run in order
rate_traces = {}
for rate in [0.1, 1.1]:
    value = 4.0
    losses = [(value - 1) ** 2]
    for update in range(12):
        value -= rate * 2 * (value - 1)
        losses.append((value - 1) ** 2)
    rate_traces[rate] = np.array(losses)
fig, ax = plt.subplots(figsize=(6, 4))
for rate, losses in rate_traces.items():
    ax.semilogy(np.arange(len(losses)), losses, 'o-', label=f'rate={rate}')
ax.set(xlabel='Update count', ylabel='Known quadratic loss', title='Only the learning rate changes')
ax.legend()
fig.tight_layout()

Read the result

Read whether successive losses shrink or grow, not just which colored line appears lower at one point. These are exact numerical optimization traces of the stated quadratic.

Change and compare

  • Try rate 0.5 on this exact bowl.
  • Try rate 1.0 and describe its behavior without calling it successful convergence.

Guided task 06

SGD and Adam under a stated budget

An optimizer includes more than a name. Plain SGD uses the current gradient directly, while Adam maintains estimates of gradient moments to adapt its changes. Their learning-rate values are not interchangeable guarantees of comparable behavior. This small comparison records two explicitly chosen settings, the same architecture, the same zero initial weights, the same batch order and the same epoch budget.

Train and validation loss serve different roles in interpreting the curves. Training supplies gradient updates; validation evaluates the resulting model without using those records for updates. The test IDs remain untouched while these choices are explored. A curve that looks better during six short epochs supports a narrow observation about this fixture and budget, not a claim that one optimizer always wins. Starting fresh models and fresh optimizers matters because reusing a model would give the second run learned weights, and reusing optimizer state could also carry history. Keep the comparison contract visible alongside the plotted result.

Try it

  1. Create a fresh zero-initialized one-layer model for each optimizer.
  2. Fit six epochs with batch size sixteen and unshuffled training data.
  3. Plot validation losses and record the optimizer settings used.
Python · run in order
optimizer_histories = {}
for name, optimizer in [('SGD', keras.optimizers.SGD(0.08)), ('Adam', keras.optimizers.Adam(0.03))]:
    model = keras.Sequential([keras.Input((1,)), keras.layers.Dense(1, kernel_initializer='zeros', bias_initializer='zeros')])
    model.compile(optimizer=optimizer, loss='mse')
    history = model.fit(batches(x_train, y_train), validation_data=batches(x_val, y_val), epochs=6, verbose=0, shuffle=False)
    optimizer_histories[name] = history.history
fig, ax = plt.subplots(figsize=(6, 4))
for name, history in optimizer_histories.items():
    ax.plot(np.arange(1, 7), history['val_loss'], 'o-', label=name)
ax.set(xlabel='Epoch', ylabel='Validation MSE (scaled units)', title='Two stated optimizer settings')
ax.legend()
fig.tight_layout()

Read the result

Compare the actual curves produced by this run. The exercise does not require a particular optimizer to win, and the tiny invented records cannot establish performance on real kitchen schedules.

Change and compare

  • Record both learning rates in a comparison note.
  • Repeat with one changed learning rate while holding the rest of the contract fixed.

Guided task 07

Batch size and update count

An equal number of epochs does not imply an equal number of parameter updates. With sixty-four training examples, batches of eight require eight updates per epoch, while batches of thirty-two require two. Both settings see the same number of examples over four epochs, but they divide those examples into different gradient estimates and perform different numbers of changes.

The code checks the optimizer iteration counter after each fit and plots that count. It also prints validation loss so the training budget can be discussed with its result. Do not attribute a difference solely to a supposed quality of small or large batches: this experiment changes update frequency as well as the grouping of gradients. A more specific comparison could hold update count fixed, but then example exposure would differ. State which budget is controlled. The final partial-batch rule also matters for sizes that do not divide the dataset. An epoch is a useful accounting unit, not a complete description of optimization effort.

Try it

  1. Fit fresh identical linear models for four epochs with batch sizes eight and thirty-two.
  2. Read optimizer.iterations after each fit.
  3. Compare total examples seen and total updates as separate quantities.
Python · run in order
update_counts = []
for size in [8, 32]:
    model = keras.Sequential([keras.Input((1,)), keras.layers.Dense(1, kernel_initializer='zeros', bias_initializer='zeros')])
    model.compile(optimizer=keras.optimizers.SGD(0.05), loss='mse')
    model.fit(batches(x_train, y_train, size), epochs=4, verbose=0, shuffle=False)
    update_counts.append(int(model.optimizer.iterations))
    print('Batch size:', size, 'Validation MSE:', float(tf.reduce_mean(tf.square(model(x_val, training=False) - y_val))))
fig, ax = plt.subplots(figsize=(6, 4))
ax.bar(['batch 8', 'batch 32'], update_counts)
ax.set(ylabel='Optimizer updates', title='Equal epochs, different update budgets')
fig.tight_layout()

Read the result

The bars count actual optimizer updates, not elapsed CPU time. Their difference follows the dataset size and batching policy, even if both fits use exactly four epochs.

Change and compare

  • Predict the count for batch size twenty before running it.
  • Write down which comparison would keep total examples seen constant.

Guided task 08

Learning-rate schedules use optimizer steps

A schedule supplies a learning rate as training progresses. The exponential schedule shown here halves its initial value every four optimizer steps, using a staircase rather than a continuously changing curve. Its horizontal unit is an update count. It is not an epoch number unless a separate calculation connects epochs to updates for the current dataset and batch size.

Inspect the schedule directly before attaching it to a long fit. The values at the boundary and just before it reveal off-by-one mistakes more clearly than an overall loss curve. The same schedule advances through its values faster in terms of epochs when there are more updates per epoch. That connection is why changing batch size can alter more than memory use. A schedule does not remove the need to choose a sensible initial rate or inspect training. This lab finishes by making those bookkeeping choices explicit: data membership, pairing, group size, optimizer state and schedule units all belong in a reproducible training record.

Try it

  1. Create an exponential schedule starting at 0.08 with a factor of 0.5 every four steps.
  2. Evaluate it at integer update positions zero through twelve.
  3. Mark the staircase boundaries and relate them to the earlier batch-size comparison.
Python · run in order
schedule = keras.optimizers.schedules.ExponentialDecay(0.08, decay_steps=4, decay_rate=0.5, staircase=True)
steps = np.arange(13)
rates = np.array([float(schedule(int(s))) for s in steps])
fig, ax = plt.subplots(figsize=(6, 4))
ax.step(steps, rates, where='post')
ax.set(xlabel='Optimizer step', ylabel='Learning rate', title='Inspect a schedule before fitting')
ax.set_xticks(steps)
fig.tight_layout()

Read the result

The rate changes at the specified update boundaries. These values are schedule outputs, not a measured recommendation for a real prediction problem.

Change and compare

  • Set staircase=False and compare the shape.
  • Explain how the number of steps per epoch changes when batch size changes.
