Arduino · Uno R3 · Lab 02

Buttons and Digital Inputs

Turn a button level into a clear instruction, then combine two requests without losing control of the output.

Lab MaterialPracticePractice Quiz

What you will learn

  • Wire a grounded button and explain its released and pressed readings.
  • Read each input and drive an LED from the current button levels.
  • Specify and test all four combinations of two buttons.

On your bench

  • Arduino Uno R3 and USB data cable
  • Breadboard and jumper wires
  • Two normally open momentary pushbuttons
  • Two indicator LEDs
  • Two 330 ohm resistors

Meet the components

Recognise the parts in the photos, then follow the labelled task diagrams for connections.

Before you build

  • Use the Uno R3 at 5 V with USB power. Disconnect USB before changing wiring. Keep D0 and D1 free for USB Serial. Upload one standalone sketch at a time; setup and loop from different tasks must not be combined.
  • Connect each button between its assigned input and GND. INPUT_PULLUP enables an internal resistor that holds the released input HIGH; closing the button connects it to ground, so a pressed button reads LOW. No external pull-up resistor is needed here.
  • Many four-leg tactile switches contain two permanently joined pairs. Identify the two switched contacts from the datasheet or with an unpowered continuity check. Using two legs that are already joined makes the input appear permanently pressed. Physical orientation varies between packages.
  • Each external LED runs from its assigned output through its own 330 ohm resistor and then from anode to cathode to GND. Verify LED polarity and breadboard connections. These are demonstration indicators, not safety controls.
  • We read held levels, not numbers of presses. Mechanical contacts can briefly bounce during a transition; no toggle or press counter is used. Hold each test combination steadily to check the intended logic. Debounced events are introduced in a later lab.

Copy one task’s sketch into Arduino IDE at a time. Replace the previous sketch before uploading the next example.

Pull-up Inputs and Conditions

Task 1 · Guided build

A hold-to-light cupboard model

digitalRead returns HIGH or LOW, but those electrical levels need an interpretation. For this grounded pull-up button, LOW means pressed. The comparison with LOW produces a bool: true when pressed and false otherwise. Naming that result pressed makes the decision easier to read. An if statement chooses one branch, and else covers the other case. Every pass through loop reads the button again and assigns the lamp state, so the lamp follows a held button rather than remembering a previous press. Separate the physical level from the meaning assigned by the application. The word pressed is not a special Arduino command; it is a name chosen for the result of the comparison. This keeps the circuit convention in one clear expression instead of scattering reversed HIGH and LOW meanings throughout the decision. Configuring an LED off in setup establishes its initial sketch state, but loop soon replaces that state using the current input. Releasing the button is therefore an action the program must keep checking, not an instruction sent only once. Test a long hold as well as a short hold. The program does not remember the number of times the button has been pressed, and it should not manufacture a repeating pattern while you keep the same level applied.

  1. Wire D2 to one switched contact of the button and its other switched contact to GND. Add the D8 LED branch shown.
  2. Upload this sketch. Test released, held, then released again. Keep the button held for several seconds to distinguish level control from a timed flash.
  3. Find the two lines that read the input and decide the output. Notice that pinMode belongs in setup, while a changing input is read inside loop.
Arduino sketch · guided example
const int buttonPin = 2;
const int lightPin = 8;

void setup() {
  pinMode(buttonPin, INPUT_PULLUP);
  pinMode(lightPin, OUTPUT);
  digitalWrite(lightPin, LOW);
}

void loop() {
  bool pressed = digitalRead(buttonPin) == LOW;
  if (pressed) {
    digitalWrite(lightPin, HIGH);
  } else {
    digitalWrite(lightPin, LOW);
  }
}

Observe and check

  • The indicator is on while the button is held and goes off after release. Holding the button longer does not generate an on/off rhythm.
  • If the LED never goes off, disconnect power and check whether the chosen button legs are internally joined.

Experiment

  • Describe the visible behaviour if the comparison tested HIGH instead of LOW, with the wiring unchanged.

Two-input Priority

Task 2 · Guided build

A request light with a quiet button

Two controls may ask for incompatible outcomes, so their priority must be explicit. Here D2 requests a light, while D3 asks for quiet and must keep it off. Read both inputs into separate named Boolean values before making the decision. The first true branch in an if / else if chain wins; only its output command runs. Testing quiet first makes the simultaneous-button case intentional. This is a logical demonstration of priority, not an emergency-stop circuit or a guarantee about wiring faults. A good test includes both controls together because separate single-button tests cannot reveal the priority rule. Also test a transition where one button remains held while the other changes. The output must follow the new combination, not the order in which you applied it. Reading each input once per loop gives two named snapshots for that pass. The reads occur sequentially, so this is not an atomic measurement of perfectly simultaneous physical edges; the demonstration is defined for held, stable combinations. Every branch writes the light, including the no-request case. That completeness prevents a previous command from surviving accidentally. Use the same reasoning when a named control moves to a different pin: the pin number locates the wire, while branch order states which meaning wins.

  1. Reuse the D2 button and D8 LED. Add a second normally open button from D3 to GND and label it quiet.
  2. Upload the sketch and test neither button, D2 only, D3 only, then both together. Release and reapply controls between tests.
  3. While holding D2, hold D3 as well, then release only D3. Keep D2 held throughout this last test.
Arduino sketch · guided example
const int requestPin = 2;
const int quietPin = 3;
const int lightPin = 8;

void setup() {
  pinMode(requestPin, INPUT_PULLUP);
  pinMode(quietPin, INPUT_PULLUP);
  pinMode(lightPin, OUTPUT);
  digitalWrite(lightPin, LOW);
}

void loop() {
  bool request = digitalRead(requestPin) == LOW;
  bool quiet = digitalRead(quietPin) == LOW;
  if (quiet) { // Quiet wins even when both buttons are held.
    digitalWrite(lightPin, LOW);
  } else if (request) {
    digitalWrite(lightPin, HIGH);
  } else {
    digitalWrite(lightPin, LOW);
  }
}

Observe and check

  • D3 suppresses the light while held. When D3 is released, the current D2 level immediately determines the next loop decision.
  • There is no remembered request and no long delay; each completed loop updates the light from newly read levels.

Experiment

  • Write a four-row table of held/released button combinations and the required lamp state before changing the priority rule.

Negation and Released States

Task 3 · Guided build

Show that a model tray is available

A logical condition can describe an absence as well as a presence. The exclamation mark reverses a Boolean value: !leftHeld is true when leftHeld is false. In this model, holding the D2 button means the tray is in use, so the availability light should be on only while the button is released. The circuit has not changed; only the application meaning of the light has changed. The conditional expression condition ? valueWhenTrue : valueWhenFalse selects one of two values. Here it chooses HIGH or LOW for a single digitalWrite. This is a compact alternative to an if/else with one output assignment in each branch. Read it as a complete choice, not as two instructions that both execute. Startup still establishes off before the first loop decision. A released button may therefore make the light turn on immediately after setup, which is consistent with the stated availability rule rather than evidence of remembered state.

  1. Reuse M1 wiring: D2 to ground through a button and the resisted D8 LED.
  2. Upload the complete sketch; interpret held as in use and released as available.
  3. Follow the electrical input and the application light separately.
Arduino sketch · guided example
void setup() {
  pinMode(2, INPUT_PULLUP);
  pinMode(8, OUTPUT);
  digitalWrite(8, LOW);
}
void loop() {
  bool leftHeld = digitalRead(2) == LOW;
  digitalWrite(8, !leftHeld ? HIGH : LOW);
}

Observe and check

  • The lamp is off during a hold and on after release.
  • Changing the meaning did not require changing the pull-up circuit.

Experiment

  • Express the same rule with an if/else while keeping the current input reading.

Independent Input-to-Output Paths

Task 4 · Guided build

Give each table position its own request light

Two buttons do not always need a combined decision. When each person has a separate indicator, keep two input-to-output paths independent. One held-state value controls D8 and the other controls D9. Pressing one button should not change the meaning or stored output command of the other path. Both lights may be on together because that is allowed by the requirement. Draw the two relationships before writing code and compare them with the pin constants or literal numbers. This catches an accidental cross-connection that might still produce a plausible response. Test each input alone, both together, and neither; then change only one input while keeping the other fixed. All outputs are refreshed on each loop pass, so there is no accumulated count or hidden priority. The result is a snapshot display of two current requests. The LEDs still need separate resistors even when they happen to light at the same time.

  1. Keep both grounded buttons from M2 and add a separately resisted LED on D9.
  2. Upload the sketch and test each control while the other is held.
  3. Confirm D2 controls D8 and D3 controls D9.
Arduino sketch · guided example
void setup() {
  pinMode(2, INPUT_PULLUP);
  pinMode(3, INPUT_PULLUP);
  pinMode(8, OUTPUT);
  digitalWrite(8, LOW);
  pinMode(9, OUTPUT);
  digitalWrite(9, LOW);
}
void loop() {
  bool leftHeld = digitalRead(2) == LOW;
  bool rightHeld = digitalRead(3) == LOW;
  digitalWrite(8, leftHeld ? HIGH : LOW);
  digitalWrite(9, rightHeld ? HIGH : LOW);
}

Observe and check

  • One person can keep their light on while the other changes their request.
  • Both-on is a defined outcome in this task.

Experiment

  • Swap the two digitalWrite destinations in a copy and predict which observed relationship would change.

Logical AND

Task 5 · Guided build

Show a two-person photograph-ready cue

Logical AND, written &&, asks whether both Boolean meanings are true. The indicator in this task represents agreement that two people are currently ready, so either person releasing their button must clear the shared cue. Form the held-state Booleans before combining them. Applying AND directly to the active-low electrical readings would describe a different condition and make the code harder to explain. The named together variable records the decision for one pass through loop; it is recalculated next time and does not retain a past agreement. A four-combination table makes the requirement complete. It also separates a failed button connection from a mistaken Boolean operator: if a single held input lights the shared cue, the intended AND rule is not being followed. No timing or press count is involved. Contact transitions can bounce briefly, so use stable holds when checking this level-based demonstration and leave event filtering for the later timing lab.

  1. Reuse the two grounded buttons and the single D8 LED from M2.
  2. Upload the sketch and test all four stable combinations.
  3. Hold both, then release one while keeping the other held.
Arduino sketch · guided example
void setup() {
  pinMode(2, INPUT_PULLUP);
  pinMode(3, INPUT_PULLUP);
  pinMode(8, OUTPUT);
  digitalWrite(8, LOW);
}
void loop() {
  bool leftHeld = digitalRead(2) == LOW;
  bool rightHeld = digitalRead(3) == LOW;
  bool together = leftHeld && rightHeld;
  digitalWrite(8, together ? HIGH : LOW);
}

Observe and check

  • A single held button never requests the joint cue.
  • Releasing either participant clears it on a later loop decision.

Experiment

  • Explain why a released input reads HIGH even though its held-state Boolean is false.

Logical OR

Task 6 · Guided build

Allow help requests from either chair

Logical OR, written ||, accepts at least one true Boolean operand, including both true together. This is useful for a shared request lamp when either person should be able to keep the request active. The rule differs from choosing only one person or giving a quiet button priority. A release by one person does not clear another person’s continuing request. That transition is an important test because checking only isolated presses can hide an incorrect implementation. Read both inputs, form one combined meaning, then write the output from that result. Avoid a pair of independent if statements in which the second button’s released case blindly overwrites a decision made from the first. One final decision should represent both current values. The task deliberately remains level based: there is no queue, acknowledgement, memory of earlier presses, or cancellation button. Those would require additional state and a more detailed contract than this current-request model.

  1. Use the same circuit as M5, but upload this new OR sketch.
  2. Hold both controls, then release just one.
  3. Compare that transition with the AND sketch without changing any wiring.
Arduino sketch · guided example
void setup() {
  pinMode(2, INPUT_PULLUP);
  pinMode(3, INPUT_PULLUP);
  pinMode(8, OUTPUT);
  digitalWrite(8, LOW);
}
void loop() {
  bool leftHeld = digitalRead(2) == LOW;
  bool rightHeld = digitalRead(3) == LOW;
  bool anyRequest = leftHeld || rightHeld;
  digitalWrite(8, anyRequest ? HIGH : LOW);
}

Observe and check

  • The lamp remains on when one of two held requests is released.
  • No previous request survives after both inputs are released.

Experiment

  • Describe the difference between OR and the exactly-one rule before attempting the independent challenge.

Complete Branch Assignments

Task 7 · Explore and measure

Diagnose a cupboard light that stays on

An output keeps its last command until another statement changes it. This can make an incomplete condition look like a memory feature even when no memory was intended. In this guided fault, the sketch turns D8 on when the button is held but says nothing about the released case. Setup turns the lamp off only at startup. After the first hold has turned it on, later released passes cannot clear it because they execute no output write. The program may compile and read the button correctly while still violating a momentary-light requirement. Compare the fault with M1’s complete if/else rather than changing wires. Identify the missing action first, then restore it. This is a software state-assignment problem, not contact bounce. Waiting longer after release cannot repair the absent instruction. Thinking in required output states for both outcomes is a useful check whenever an indicator should follow a current condition.

  1. Start with the M1 circuit and sketch. Remove only the else branch that writes LOW in loop.
  2. Upload the altered sketch, hold the button once, then release it.
  3. Restore M1 after identifying the missing release action.

Observe and check

  • A successful compile does not establish complete behavior.
  • The restored M1 sketch clears the output on release.

Experiment

  • Explain why putting another off write only in setup would not fix the later release.

Observation Rate and Responsiveness

Task 8 · Explore and measure

See why a slow loop can miss a brief request

A digital input is observed when the sketch calls digitalRead, not continuously by every line of the program. Adding a long delay after the lamp update postpones the next observation. A brief hold that starts and ends during that pause can be missed entirely, while a sustained hold will eventually be sampled. This experiment uses the M1 momentary sketch and adds a 600 ms delay at the end of loop. It does not count events or remove bounce; it simply reduces how often the current level is checked. Timing relative to the sampling instants determines the result, so individual hand-operated taps need not give identical outcomes. Compare a long hold with several short taps and distinguish a specified illustrative timeline from what you actually observed. Restore the fast version afterwards. Later nonblocking timing will allow periodic output actions while keeping input checks frequent, but this task first makes the limitation of delay visible.

  1. Use the M1 circuit and add delay(600) at the end of its loop, after the complete if/else.
  2. Upload the changed sketch and compare long holds with brief taps.
  3. Restore M1 with no delay after recording the responsiveness difference.

Observe and check

  • Some short taps may have no visible effect.
  • The no-delay version services level changes more frequently.

Experiment

  • Explain why increasing delay is not a valid way to make a reliable press counter.
